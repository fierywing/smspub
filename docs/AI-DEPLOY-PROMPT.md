# smspub AI agent 部署提示词

把下面整个代码块复制给能够访问项目源码和目标 Linux 主机、执行命令并修改文件的 AI agent。默认参数适用于首次在当前主机部署；已有服务会先识别并沿用。需要指定服务器、域名、通知通道或真实测试号码时，修改开头参数即可。

“一键”是指一次交代任务后让 agent 连续完成检查、实施、验收和交付。硬件能力、运营商服务、证书信任和人工听音无法仅靠提示词保证；缺少条件时，agent 必须准确标记未完成项。

```text
请作为本项目的部署工程师，直接完成 smspub 的部署、验证和交付，不要只给出计划或让我逐条执行命令。以实际仓库和目标机器为依据；对已授权范围内可自行完成的步骤持续执行，遇到错误先定位并修复，再继续验证。

【部署参数，可按需修改】
- 源码目录：当前项目仓库；若不存在，先从明确的项目上下文查找；多个候选无法确定时询问，不能修改无关同名仓库。
- 目标主机：当前已连接主机；若另有明确指定的 SSH 主机则使用它。禁止猜测登录凭据。
- 部署方式：优先沿用现有方式；全新 Linux 主机默认 Docker Engine + Compose，不适用时选择二进制 + systemd。
- 部署目录：已有部署沿用原目录；新部署默认当前普通用户的 ~/.local/share/smspub。需要原生服务时按 docs/DEPLOYMENT.md 使用专用系统路径。
- 访问方式：默认仅本机 127.0.0.1:8080，可交付 SSH 转发方案。若我已指定可信局域网/域名，则按该要求配置；未经指定不要开放公网端口。
- 功能目标：短信网关和 Web 管理；在实际硬件与固件支持时配置浏览器通话。未支持项如实列出。
- 通知凭据：优先保留已存在配置；没有凭据时不虚构、不启用无效通道。
- 真实短信/电话测试：默认不主动向真实号码发送或拨号。仅在我已经授权并给出测试对象时执行；否则完成模拟、只读检查，并保留人工验收项。
- 服务切换：本提示词授权为部署进行必要的本项目启停/重建；先备份并完成候选版本验证。若检测到正在进行的通话，等待空闲或询问中断时机。
- 系统依赖：可安装本项目必需且不会替换/中断现有基础设施的依赖；已有 Docker/代理等优先复用。不创建收费云资源，不改变无关服务或全局防火墙策略。

【首先阅读并核对】
1. 读取适用的 AGENTS.md，以及 README.md、docs/README.md、docs/PROJECT.md、docs/DEPLOYMENT.md、docs/CONFIGURATION.md、docs/OPERATIONS.md、docs/API.md。
2. 核对 go.mod、Dockerfile、全部实际生效的 Compose 文件、cmd/smspub/main.go、cmd/smspub/tls.go、internal/model/model.go、internal/config/config.go、internal/hub/hub.go、internal/web/ 路由。文档与源码不一致时以实际实现为准并说明。
3. 记录 Git 提交和工作区状态；保留未提交改动。不要 git reset --hard、覆盖私有配置或读取无关项目的凭据。不要把旧的 ./smspub 二进制当作当前源码构建结果。

【必须遵守的项目事实】
- 这是 Go 单二进制项目，前端通过 embed 编译；无需 npm build、Redis、外部 SQL 或独立 Python 生产服务。
- 当前 go.mod 要求 Go 1.27.1，Dockerfile 使用 golang:1.27-alpine；执行时再次核对，不擅自降级 go.mod/go.sum。
- 配置由 -c 指定；数据目录固定为进程工作目录下 ./data。容器工作目录 /app，持久化 /app/conf 和 /app/data；systemd 必须固定 WorkingDirectory。
- 配置保存使用同目录临时文件和 rename，只能挂载整个 conf/，不能单文件挂 config.json。
- -listen 优先于 JSON listen；程序没有业务环境变量加载机制。Compose .env 只用于编排参数。
- 程序没有内置登录、密码或 API Token，GET /api/config 会包含凭据；HTTP 200、CSRF 和麦克风 session 均不等于鉴权。
- POST /api/config 是完整替换，读取最新值并保留字段；不要用只含一两个字段的 JSON 覆盖已有卡片/通知。不要打印完整配置。
- 默认自动扫描会接触可见串口；隔离测试必须 auto_cards=false、空 channels、独立 data，不能访问生产设备。已有真实服务不得与测试实例共用配置、数据库或串口。
- 优先使用实际 /dev/serial/by-path/...，读真实设备 GID。容器补充组和设备 cgroup 都要配置，不能假定 dialout=20。
- 仓库设备映射为 /dev:/dev 加 c 188:*、c 166:*、c 189:*；检查 sysfs 和目标设备实际权限。不得用 privileged 或 chmod 777 绕过问题。
- 浏览器麦克风要求安全上下文与授权；USB 语音取决于实际模组、诊断口和固件。当前上行固件要求 ML307A-DSLN-MTSH1S00，禁止绕过白名单或对未知固件写内存/刷机。
- HTTPS 是额外监听，三参数必须齐全，原 HTTP 仍在；证书不会自动申请或续期。仅开启 HTTPS 不会增加认证。
- 没有 /healthz；用 GET /api/cards 检查 HTTP 服务，返回 [] 只代表服务可用。online=true 或 voice.supported=true 不能替代真实收发/通话验收。

【按顺序执行】
一、只读检查
- 确认目标主机身份、系统、架构、磁盘、权限、已有进程、容器、监听端口、服务管理方式、部署目录和挂载。
- 检查 Docker Engine/Compose 或 Go/systemd 的可用性。Linux VM/容器需验证 USB 直通，不能假设 Docker Desktop/rootless 具备设备访问能力。
- 查找本项目现有实例及实际 Compose project/file 列表、override、.env；只提取必要的非敏感信息。若缺 SSH/主机身份等必要信息，集中询问，同时继续无依赖的源码检查和构建准备。
- 查看 USB/串口/by-path、实际 UID/GID 和权限，识别其他占用者。存在正在工作的 smspub 时，通过它的只读 API/AT 队列核对，不能另开串口争抢。

二、准备候选版本
- 选择当前源码构建，使用唯一镜像标签并记录提交/工作区状态；或使用明确版本并核对功能的发布镜像摘要。latest 不保证包含当前源码功能。
- 执行 go test ./...、go vet ./... 和构建；使用普通用户运行权限测试。若只有 root 环境，建立受限测试用户或使用非 root 构建容器，不能改测试放行。
- 涉及网页电话时运行 node --test tools/test_callaudio.cjs；涉及辅助工具时运行 python3 -m unittest discover -s tools -p 'test_*.py'。依赖/网络缺失与测试失败分别记录，不伪造通过。
- 在隔离运行目录先进行无设备 HTTP/JSON/静态资源启动检查；可按部署文档用假模组验证单条短信、长短信、管理员转发。测试不挂生产 /dev，不连接真实通知服务。
- 构建/验证失败时不得切换现有运行服务。可修复范围内的部署配置问题；若需要改变业务逻辑或硬件协议，先清楚说明原因和范围。

三、持久化与部署配置
- 已有部署先记录原镜像 ID/二进制校验值、入口和服务参数，保留可用的旧版本。确认没有正在进行的通话后，短暂停服做一致性备份，备份 conf、data、编排/服务文件；备份失败则恢复原服务并停止切换。
- 新部署从 docs/examples/ 复制模板到专用目录，不覆盖已有文件。填实际镜像、UID/GID、设备 GID、IP/端口；确保 conf/data 所有者正确且凭据文件为私有权限。
- Docker 使用显式 -f、--env-file 和固定 -p，沿用已有项目身份。用 docker compose config 验证最终配置，不能让 override 合并后意外保留对外开放端口。
- systemd 使用专用服务用户、真实串口组和固定工作目录；不得设置 PrivateDevices=true 隐藏模组。
- 只在确有需要且已识别目标 VID/PID 时配置 USB 复位 udev 规则；不复位其他 USB 设备，不为“试试看”刷固件或运行 IMS 实验。
- 保留已有卡片 ID/IMEI、号码、通知凭据和历史。缺凭据时保留可用核心服务，集中列出未完成通知项；不生成看似有效的假密钥。

四、入口与启动
- 按授权入口限制绑定地址；公网/不可信网络入口在开放前配置 HTTPS 与认证，并确保原始 API 端口不可绕过认证。
- HTTPS 代理保留原始 Host，关闭音频响应缓冲并允许长连接；原生 HTTPS 配好三参数、证书权限和端口。证书必须在真实客户端受信任；不要用 curl -k 作为最终验收。
- 启动单个正式实例，查看进程状态、日志、实际端口/挂载和容器内设备权限。不因为第一次失败就关闭安全控制或覆盖已有数据。

五、分层验收与恢复
- 服务层：首页和关键静态文件返回成功；/api/cards 为 JSON 数组；没有持续重启或致命日志；运行用户能持久化配置/数据库。
- 持久化层：在新部署或维护允许时验证受控重启，配置和已有历史保留。不得通过删除真实数据或额外发送真实短信制造测试条件。
- 设备层：等待合理探测窗口，逐卡对应实际模组、检查在线状态和只读 AT 信息。设备数量不足时说明缺哪张卡、证据与排查结果。
- 业务层：仅执行已授权的真实测试；确认接收方短信、推送、通话声音及挂断释放。AT OK、CLCC active、模拟测试不替代收件方/人耳确认。未授权或缺硬件时标为待验证。
- 失败恢复：保留错误日志并脱敏；切换失败优先恢复旧镜像/二进制及配置。数据库回滚前保留失败后数据，避免丢失新短信；不得无提示恢复旧备份覆盖新数据。
- 不执行 down -v、rm -rf data、清空数据库、破坏性 Git 清理；不要全局停用 ModemManager、其他串口应用或防火墙。必要时仅处理已确认且获授权的冲突对象。

【最终交付】
请给出并在部署目录保存一份私有的脱敏部署报告（不要入库）：
1. 总体结果：完成 / 部分完成 / 受阻；明确成功的层次，不能使用“完美部署”代替证据。
2. 主机、架构、源码版本、镜像 ID/摘要或二进制校验值、实际部署目录。
3. 可直接使用的访问地址；若仅回环，提供适用的 SSH 转发方法；不得交付不可访问的伪地址。
4. 启动、停止、重启、查看日志、升级和回滚的准确命令，包含实际路径、项目名和文件参数。
5. 配置/数据/证书/备份位置、运行身份和恢复版本；只给位置和脱敏摘要，不展示密钥、短信正文、完整号码。
6. 验收表：每项标明通过、失败、待人工验证或不适用，并给出实际证据。
7. 无法完成项、具体阻碍、已完成的独立工作，以及我还需提供的最少信息。
执行过程中简短报告关键发现；尽量一次收集真正缺失的信息，不为已经授权的常规步骤反复请求确认。完成后再交付最终结果。
```

## 已有仓库时的简短启动指令

如果 agent 已经打开本项目，可以只发送：

```text
请读取并执行 docs/AI-DEPLOY-PROMPT.md 中的完整部署提示词，按 docs/DEPLOYMENT.md 和 docs/OPERATIONS.md 在当前目标主机完成 smspub 部署。沿用已有配置和数据；首次部署默认仅绑定本机，优先 Docker Compose。完成构建、备份、分层验收和回滚准备，交付实际访问方式及脱敏报告。不要把服务启动或模拟通过写成真实短信/通话验收通过。
```
