# ML307A 连续 USB 上行与网页麦克风

2026-10-24，实板 card3，固件 `ML307A-DSLN-MTSH1S00`、CP DB `0x4AED`。仅 USB 连接，使用原 SIM 号码。

已实现浏览器采集 → 同源 HTTP → Go 双缓冲 → USB interface 04 → 模组远端混音的连续音频通路。之前只验证了 AMR 文件播放；本次连续通路不写音频文件。网页保留拨号、接听、挂断和 USB 收听，增加麦克风权限请求、接通后自动发送、静音与取消静音。

## 已取得的证据

- 实机诊断内存命令成功写入自主分配的 4096 字节 RAM，并读回核对。测试分配均已释放。
- `AudioHAL_TestMediaLoopback` 与远端路由结合，可启动持续内存播放。4 kHz 输入被固件重采样到 16 kHz，播放器回调持续运行；停止后任务标志、采样率及路由均恢复。
- 一通真实电话接通后，连续发送 300 帧、约 6 秒的循环变调音，随后停止播放并自动挂断。远端混音日志有非零数据；**该次电话的人耳听感仍待用户确认**，不能沿用早先 AMR 文件播放的“清楚听到了”作为本次连续流的验收。
- 最终 Go 适配器独立运行 20 秒：提交 1005 帧，观察到 998 个远端混音 PCM 帧、100 次测试音变化，结束复位成功。提交数含最后的少量排队帧，不能用两数差值直接计算丢帧率。
- 真实 Firefox AudioWorklet / MediaStream → HTTP → 最终 Go 适配器 → 实机 USB 验证：45 个音频 POST，模组远端混音中识别出 226 帧匹配测试音，62 帧静音。静音、取消静音、停止后音轨 ended，以及模组复位均通过。浏览器输入为生成的 700/1100 Hz 测试 MediaStream，未采集主机真实麦克风；此测试模拟 active 呼叫状态，Hub 未启动，未扫描其他串口，未拨号。

用户随后确认网页已经可以通话，但反馈中途经常出现“USB 音频断开”，麦克风和收听需手动重开。真实通话链路已由用户使用确认，长期稳定性、清晰度和时延仍需继续验收。

## 固件入口与连续缓冲

公开的带符号 MBRH SDK 仅用于定位，实际入口和数据地址已在 MTSH 实机只读核对。当前实现只允许已核对的固件；版本、DB 常量、函数表或 HAL 指针不符即拒绝。

| 实机命令 | 函数与用途 |
|---|---|
| 530，`0x8030f1cb` | `AudioHAL_TestMediaLoopback`，奇偶切换启动／停止 |
| 532，`0x8030f355` | `AudioHAL_VoiceRecord`，初始化测试缓冲并停止不使用的本地录音任务 |
| 666，`0x80062063` | `armRead32`，只读状态与缓冲指针；应答 `(42,9320)` |
| 668，`0x800620ad` | `armWrite32`，写入指定音频 RAM 字段或缓冲；应答 `(42,9322)` |

HAL 起点 `0x7e40645c`；`+0x50` 是播放到远端的开关。已核对 `AudioHal_AifPlay2Farend` 仅设置此字段并记录日志。测试状态区为 HAL `+0x80`，其中 `+0x1c` 为输入采样率，`+0x20` 为 3840 字节测试缓冲的指针。

先在远端路由关闭时初始化并停止录音任务、清空音频缓冲，再启动远端播放并停掉封装函数附带的录音。主机在该分配的前两帧之间交替写入，每帧 80 样本／160 字节／20 ms；整帧写完并核对每个字的应答后，才以单次 32 位写发布缓冲指针。这样播放回调不会读到正在更新的半帧。

退出时停止发送与播放，清零两帧，恢复原始缓冲指针、8 kHz 测试采样率及近端路由。写入器仅允许这三个已核对的音频字段及返回分配的前两帧；不能对任意地址写入。没有写 flash、改程序代码、刷固件或访问 RNDIS 接口。

当前采用 **4 kHz、单声道、16 位 PCM**，输入语音频带较窄。逐字应答的 8 kHz PCM 实测缺少稳定带宽余量；不能把 USB 物理速率当作诊断命令可用速率。多条命令拼在同一个传输中会被固件丢弃，直接 libusb 访问也未解除这一限制。使用串口驱动即可完成当前方案，无需生产环境重绑定接口。

## 网页与生命周期

- 通过 HTTPS 或 `http://localhost` 打开网页，浏览器才允许真实麦克风。远程主机可经现有 HTTPS 代理，或 SSH 本地转发到 localhost。普通远程 HTTP 页面仍可拨号／收听，但浏览器会限制麦克风。
- 拨号／接听的用户操作请求麦克风权限；拨号前也可点“开启麦克风”检查权限并准备设备，接通后才发送；再次点击或空闲时关闭电话窗口会停止采集。权限未允许时仍可控制电话和收听。
- AudioWorklet 先低通，再输出 4 kHz PCM；每约 100 ms 上传五帧。音频仅发送到当前服务，不写录音文件。
- 接收与发送共用一个诊断口 owner。每次会话使用随机令牌；错误令牌、旧序号、非法长度和非 active 呼叫拒绝。队列最多 200 ms，网络积压丢弃旧帧。
- 无数据时持续发送全零静音帧，不再设置无麦克风数据的超时退出。短暂 USB／网络中断会自动重连并保留原麦克风音轨及静音选择；挂断、手动停止或关闭网页时停止音轨并清理设备状态。用户应查看浏览器的麦克风授权与设备选择；实际通话建议耳机。

实现：`internal/voice/uplink.go`、`internal/web/microphone.go`、`web/callaudio.js`、`web/microphone-worklet.js`。协议见 [后端文档](BACKEND.md)。固件相关代码必须随固件变更重新验证。

## 局域网 HTTP 的麦克风限制与 HTTPS 入口

用户实际通过 `http://192.168.31.167:8080/` 访问；该来源不属于浏览器安全上下文，`getUserMedia` 不可用。按钮先前还要求 active 通话，现允许在拨号前准备麦克风，并在按钮旁直接显示无法开启的原因；后台仍要求电话接通后才能发送。

本机已增加 `https://192.168.31.167:8444/`，HTTP 8080 继续提供服务。局域网自签名证书含该 IP、127.0.0.1 和 localhost，证书／私钥保存在已忽略的 `conf/tls/`；私钥权限 0600，未入 Git。首次访问需在浏览器接受该本机证书；正式环境可换成受信任的证书。配置通过本机的 `docker-compose.override.yml` 提供 HTTPS 端口和启动参数。

## 2026-10-24 音频中断恢复修复

旧版将所有流读取失败统一显示为“USB 音频已断开”，没有记录底层原因，因此不能仅凭提示认定 USB 物理掉线。本次检查的最近两小时内核日志未见对应 USB 断连或重置；旧程序存在下列可复现的过早退出条件：单次 200 ms 原生命令应答超时、单次 1.5 秒麦克风 HTTP 超时、两秒上传空档，以及通话查询暂时失败。

修复内容：

- 命令泵可在日志序号跳变后识别独立的完整原生命令应答，并核对当前等待的类型、地址及写入值，避免等待下一条日志导致误超时。普通 PCM 解码器保留原同步规则。
- 仅对受限音频 RAM 写入 668 最多发送三次，每次等待 200 ms；读状态最多等待 600 ms。切换命令 530／532 不重发，USB 写本身失败也不盲目重试。
- 上传停顿时持续补静音，由通话状态与连接生命周期决定何时结束，不按无新块时长退出。浏览器对单个失败上传丢弃旧块；连续三次失败或会话过期才重连。单次上传等待上限五秒。
- 音频流关闭／错误自动重连，保留同一个 MediaStream 和静音选择，以 0.5／1／2／4／5 秒退避，通话期间持续重试，不再因达到八次中断而停止；持续十秒的连接会重置退避计数。十秒没有流事件会取消挂住的连接。
- 实际 Firefox 会在禁用音轨后停止部分源图的处理，静音状态重连时可能没有 worklet 帧；worklet 缺输入时补零，并为被浏览器停调度的静音图增加上传静音保活。音轨仍保持禁用，恢复时不会发送过期语音。
- AT 状态查询错误继续使用缓存中的 active 呼叫，不凭单次查询失败停止音频；网页对离线／空呼叫快照等待四秒确认。主动挂断及服务端确认通话结束仍立即停止，不重连。
- 服务端日志记录具体的读取／USB 应答／写流错误；浏览器通过错误事件的 retry 字段区分暂时中断与通话结束。不保存语音数据。

验证：Go 全量 race 检查通过；新增命令丢应答、错误值应答、孤立应答重同步、重试上限、短上传停顿及通话结束测试。Node 测试覆盖音频流恢复、上传错误、静音保留、停止重试、设备移除和无输入静音帧。

实板 card3 空闲连续传输 120 秒：提交 6005 帧，收到 5998 个远端混音帧、600 次变调，结束复位成功；不拨号、不读取真实麦克风、不保存音频。该结果验证 USB 连续传输，不替代真实通话的长期听感验收。

真实 Firefox AudioWorklet 恢复验证通过：同一麦克风及静音状态跨 USB 错误恢复、一次上传失败与两秒上传延迟、连续三次上传失败后的新会话恢复、确认结束后停止音轨及重试。前端回归现共九项通过。本机 Docker 已更新为 `b945b7bd0090`，保留 `smspub:before-audio-recovery-20261024`；HTTPS 8444 证书校验、新音频资源与磁盘一致、五卡在线检查通过，生产 Firefox 的麦克风准备／取消也通过。本轮未发起真实电话。


## 通话全程静音保活

按用户要求，接通后在无语音输入时使用全零 PCM 保持音频流，直到任一方挂断；也响应手动停止、关闭网页与真实硬件／网络错误的清理。零 PCM 表示数字静音，不生成超声波、低音量音调或提示音。

浏览器在没有 worklet 帧超过 200 ms 后，每约 100 ms 上传五帧静音，不再只对“已静音”的麦克风启用此机制。服务端无排队语音时每 20 ms 写一帧 160 字节静音，不因 15 秒无新上传而退出。正常采集恢复后立即使用新的语音帧，旧语音不补播。临时故障沿用现有重连机制，并移除八次失败退出限制；任一方挂断的事件、手动停止及页面关闭都会取消保活和重试。

回归测试覆盖：无任何上传时持续写静音、取消上下文后停止并复位；未静音但采集停顿时持续上传静音，恢复后传语音；十次连续音频中断后仍能恢复，挂断后停止。Go voice/web race 检查及 Node 十一项检查通过。

实板验证命令：`sudo /tmp/smspub-uplinkcheck --card card3 --idle --seconds 25 --pause-input 18s`。全程未拨号；人为暂停上传 18 秒，收到 1248 个远端混音 PCM 帧，其中 901 个为静音，恢复输入后识别到 296 个测试音帧；结束时音频设置复位成功。结果验证静音供流及恢复，不代替电话对端听音验收。

本机服务已更新为 `830aba3fc1b5`，上一版保留为 `smspub:before-silence-keepalive-20261024`。生产 HTTPS 新音频资源一致，五卡在线，无进行中的通话。
