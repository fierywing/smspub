## 本次需求约束

用户明确要求仅通过 USB 和程序完成拨号、接听及电脑／浏览器双向语音，不使用模组 MIC/SPK 等传统模拟音频口。因此，外接声卡或复用系统声卡并接模拟音频线的方案不符合本次需求，不作为待实施方案。

现有实现完成了 AT 通话控制。上传的 AT 手册未说明通话 PCM 的 USB 导出接口，但后续实测已通过 USB 诊断日志恢复可懂的通话音频；现有独立工具提供增量录音和浏览器实时试听，详见 [诊断口 PCM](ML307A-DIAG-PCM.md)。2026-10-24 又经真实电话验证 USB 上传 AMR 后播放到远端，用户确认清楚听到测试音，详见 [USB 上行记录](ML307A-DIAG-TX.md)。电脑麦克风连续实时上行仍未实现。另一个主机 IMS 候选路线见 [纯程序软电话方案](ML307A-SOFTPHONE.md)，接入尚未打通。

## 结论

ML307A-DSLN 支持 VoLTE 和模拟音频，可以使用 AT 指令拨打、接听、查询及挂断。**这不等于能够通过 USB AT 串口传输通话音频。**

音频手册明确不支持 PCM 流播放与录制；硬件、EVB、扩展 AT 及 Android RIL 手册中，未找到可用于双向通话的 USB Audio Class（UAC）或其他实时数字音频接口说明。因此，不能依据这份资料实现“导出模组内部通话 PCM 到电脑／浏览器”。这项结论仅针对模组音频导出，不排除主机自行运行 IMS／SIP、通过 IP 数据传输语音的方案。

用户确认当前只有 USB 连接，没有音频转接硬件，并明确排除模拟音频接线。呼出、来电接听与挂断均已于 2026-10-23 实板验收通过（见下节）；诊断音频接收、文件上行、连续内存上行及网页麦克风现均有程序实现，后者的最终验证范围见 [连续上行记录](ML307A-DIAG-STREAM.md)。

## 实板呼出验收（2026-10-23）

代表卡 `card3`（电信 460-11），固件 `ML307A-DSLN-MTSH1S00`，经 smspub 的 `POST /api/cards/{id}/call` 与 `AT+CLCC` 轮询完成，未直开串口。拨打真实测试号码（用户指定），完整状态流转与结论：

| 步骤 | 观察 |
|---|---|
| 前置 | `AT+CEREG: 2,1`（LTE 归属注册）、`+CSQ: 31,99`、`+CGDCONT` 含 CID 8 `IMS` 上下文 |
| `ATD<number>;` | 返回 OK，CLCC 立即出现 `direction=out state=dialing mode=0` |
| 对方振铃 | CLCC 刷新为 `state=alerting` |
| 对方接听 | CLCC 刷新为 `state=active`，`mode=0`（语音）与手册枚举一致 |
| `ATH` 挂断 | 固件返回 `NO CARRIER`（非 OK），呼叫列表回空、通话实际已结束 |

由此确认的两个固件行为及适配（已入 `internal/modem/call.go`）：

1. **`ATH` 挂断成功以 `NO CARRIER` 结束命令**（Hayes 传统语义：载波释放即成功）。程序原样报错会误导用户重复挂断；现 hangup/answer 对呼叫结果行（NO CARRIER/BUSY/NO ANSWER/NO DIALTONE）视为已执行，以随后的 CLCC 复查为准。
2. **固件在呼叫状态变化时主动上报 `+CLCC:` 行**。该行若恰逢 `AT+CLCC` 查询在途，会被 AT 层并入命令响应，同一呼叫在解析结果中出现两次；实测拨号响应即出现重复条目。按 27.007 呼叫 idx 的唯一性去重后，重复的来电条目不再卡死 answer 的单通校验。该上报行同时纳入通话事件触发即时刷新。

## 来电接听验收与 USB 音频取证（2026-10-23）

同日续测：真实来电（测试号码呼入 card3），CLCC 上报 `direction=in state=incoming mode=0` 且带主叫号码，程序经 `ATA` 应答后 1 秒内状态转 `active`，通话保持 5 分钟后经 `ATH` 挂断回空闲。**来电接听全链路实板验收通过**；至此拨出、接听、挂断三项控制均已在实板验证（含振铃上报号码显示）。

通话保持期间（对端持续说话）做了 USB 层音频取证：**在该次未连接诊断客户端的测试中，仅见 AT 控制流量**。这一观察不能排除握手后诊断口输出音频。

| 检查 | 结果 |
|---|---|
| `AT+MAUDRECSTREAM` / `AT+MAUDPLSTREAM` | 通话中实测均返回 `AT ERROR`（固件拒绝，与手册"PCM 流录放不支持"一致） |
| usbmon 全总线抓包（358 秒，覆盖整段通话） | card3 所在设备（经 CLCC 流量定位）仅有 AT 通道字节：Bulk IN 共 9.3 KB（约 26 B/s，全部为 CLCC 轮询应答、心跳与 URC），Bulk OUT 约 4.4 B/s；其余模组仅心跳。无任何端点出现持续数据流 |
| 数量级对照 | 即便最低码率 AMR-NB（4.75 kbps ≈ 0.6 KB/s）5 分钟也应有约 180 KB，PCM 8 kHz/16 bit 约 3.4 MB；实测 9.3 KB 与纯 AT 控制流量完全吻合 |

原始抓包与含号码的临时日志测后删除（仅保留上述汇总），usbmon 模块已卸载。**更正：此前据此推断“量产固件没有诊断音频、只剩模拟音频或 Host IMS”不成立。**同日后续测试连接诊断口后抓到连续 PCM，录音已由人耳确认可懂；详见 [诊断口实测](ML307A-DIAG-PCM.md)。CATStudio 分析报告中的老平台命令表不能直接套用，不代表诊断接收通道不存在。

该次控制验收未验证程序双向音频和非电信卡。后续诊断录音的可懂性不等于已实现程序发送声音。

## 模拟音频桥接参考（不符合本次需求）

当模组接在运行 smspub 的主机上时，后续可实现的通路是：

```text
浏览器麦克风／扬声器
       ⇅ 网络音频
smspub 主机上的音频桥接程序（待实现）
       ⇅ 采集／回放
支持采集和回放的声卡（系统自带或 USB）
       ⇅ 差分／单端、电平和偏置匹配电路
ML307A-DSLN 的 MIC_P/MIC_N、SPK_P/SPK_N
```

系统自带声卡可以复用，不要求购买 USB 声卡。声卡必须有采集与回放能力；只有播放能力的 HDMI 音频或仅有扬声器输出的转接头不足以双向通话。模组音频引脚为差分信号，不能将这些引脚当作普通电脑耳机／麦克风插孔直接接线。匹配电路及接点必须依据具体开发板原理图和声卡规格确认。仅有 USB 连接时，系统存在声卡不会自动连通模组音频。

如果声卡接在浏览器所在电脑而非 smspub 主机，音频设备位置及路由方案会不同，不能套用远端主机桥接配置。

2026-10-22 在当前开发主机进行的只读枚举显示：`Intel 82801AA-ICH` 的 `card 0, device 0` 同时列有采集和回放，`device 1` 为额外麦克风采集；HDMI 设备只有回放。系统运行于 KVM，枚举结果不能证明宿主机物理音频插孔已经映射至虚拟机，也不能证明已经连到模组。本次未录制或播放音频。若 smspub 部署在这台虚拟机，还需核对其宿主机音频后端和实际模拟输入／输出路径。

仓库当前 Docker 配置虽然挂载 `/dev`，但只放行串口和 USB 主设备号，未放行本机声卡节点的主设备号 116。后续音频桥接还需按实际部署配置声卡设备权限和采集／回放工具；当前未修改部署配置或重启运行中的服务。

## 模拟音频方案的验收参考（不作为本次实施计划）

1. 核对具体开发板音频接口和固件版本，读取 ATI、CGMR、CPIN、CEREG、CLCC；LTE 注册不等于 VoLTE 注册。
2. 先以板载模拟音频验证一通呼出、一通呼入、双向说话及挂断，保存脱敏后的 CLCC 原始返回以确认 mode。
3. 接好音频匹配电路和双向声卡，确认声卡单独采集、回放正常。
4. 完成浏览器音频桥接，验证双向实时声音、断线停止采集、挂断和设备重新连接。

模拟 AT 测试仅覆盖控制协议、状态和并发，不代替真实音频验收。CATStudio 包内 PXA 命令表尚未与 ML307A（ASR1606）匹配，不能据此确定通话上行注入接口；USB 诊断口的接收通道已有另行实测，不受这个命令表缺失的否定。
